# Design Principle — Dual-Outcome Branching

**What this is:** a generalized, portable version of a rule one specific project used for every companion
character's personal-arc resolution. Fully optional — relevant only if your project wants branching character
resolutions with real, mechanically-distinct outcomes; skip entirely for a linear-arc project.

---

## The Core Rule

A character's personal arc resolves into **2 to 5 mutually exclusive outcome branches**, not one single
resolution. Each branch is a genuinely different way her story ends, not a minor cosmetic variant of the same
underlying outcome.

**Branch count policy:** 2 is the floor, 3 is a healthy default, 4 is comfortably supportable, 5 is a hard
cap. Beyond 5, branches start cannibalizing each other's distinctiveness and the design/writing cost stops
paying for itself in meaningfully different content.

## Why Mutual Exclusivity Matters

The branches have to actually compete for the same narrative "slot" — picking one should foreclose the others
for that playthrough. A set of outcomes the player can freely combine or sequence through isn't branching,
it's just a checklist. The whole value of this pattern is that a specific choice, made once, meaningfully
closes off other futures for this character.

## Every Branch Needs a Real Trade-Off

See `No_Good_Endings.md` for the fuller principle this rule is a specific application of — no branch is
allowed to be a clean win with no downside. Every branch needs to gain the character (and the player) something
*and* cost her something else, genuinely, not just a smaller version of the same gain. A real-world worked
example: one character's arc resolved into three branches, each restoring a different balance of what
she'd lost, with no branch reading as strictly better than the others once the costs were made explicit —
retroactively corrected into this shape after an earlier draft let one branch read as a clean "good ending."

## Optional Additive Layer: Branch-Gated Content

A further pattern worth considering on top of the base rule: each branch can also unlock genuinely exclusive
world content through the character herself — a location, a service, a relationship, something the player
only gets access to *because* they chose that specific branch for her. This gives branching real weight beyond
the character's own personal story, without requiring it.

## How This Interacts With the Rest of the Pipeline

- **Stage 4** (`../Pipeline/04_Story_Material.md`) is where the underlying conflict that eventually branches
  gets built — the Contagonist, Impact Character, and Revenant material there is often what each branch ends
  up dramatizing a different resolution of.
- **Stage 5** (`../Pipeline/05_Beats_Paths_Results.md`) is where each branch gets its own Midpoint mechanic,
  its own beat sequence, and its own slot in the Ending-Shape Cross-Mapping Table — each branch is treated as
  its own complete arc for structural purposes, since "the Midpoint" and every other beat is defined by
  functional role, not fixed timing, and different branches can genuinely diverge before their shared arc even
  reaches its own structural midpoint.
- **Arc-Space Enumeration** (the leading section of `../Pipeline/05_Beats_Paths_Results.md`) is the recommended
  *source* of candidate branches for a non-linear project, rather than inventing 2-5 branches directly: it
  generates one full candidate arc per Arc Type against the same fixed character, screens out whichever ones
  are genuinely implausible given her already-established psychology, and hands the survivors here for final
  curation. If more than 5 plausible candidates survive that process, use this rule's own distinctiveness
  standard (a branch earns its slot only for a genuine trade-off, not a flavor variant of another survivor) to
  cut down to the strongest 5 — don't silently exceed the cap.
